核心判断

宿主先准备“能做什么”

Mode handler 产出 systemPrompt、tools、permissionMode 等配置。Backend 解析 CLI 路径和环境，准备 MCP，取得 runtime，连接 ACP，再 load/resume session。每阶段记录独立耗时，而非只有一个“启动慢”。S01S05

初始化完成后，prompt 请求携带 sessionId 发到 ACP connection。消息更新、工具提问、权限请求沿回调通道返回 App；它们不是模型最终文本的附注。S31S33

能力逻辑在执行时逐步展开

Skill 的作用是给模型方法与资源入口；MCP、脚本或宿主工具提供实际动作。结果进入后续判断，最终由领域流程决定怎样保存、检查和展示。S09S11S24S26

图中的“模型 → 工具 → 结果”是基于工具配置、Hook 和领域流程归纳的执行模型。本轮没有完整还原所有模型 provider 的内部循环，也未认定某个 SDK 是唯一主引擎。

02

上下文是一条装配流水线

模板、身份、历史、记忆和能力说明，各有不同生命周期。

实现

PromptRenderer 的顺序收集

代码中的 collectors 依次处理环境与语言、身份、个性化、工作记忆、云端用户记忆、协作、专家提示、专家管理、二进制工具环境，再注入 native runtime 可用性。S04

收集器可以 warmup；同一次收集的变量挂在 options 对象上复用，避免渲染时再次收集。renderUserContext 单独生成首条用户消息的隐含上下文。S04

设计含义

稳定规则与易变状态分离

通用系统模板可以复用；身份、口吻、用户指令等通过独立 user context 注入。专业知识则按 Skill 触发加载。由此推断，这种拆分有利于降低重复装配和上下文耦合；实际缓存命中率和 token 收益未测量。

身份与记忆不是“都塞到 system prompt”这一个通道。修改上下文时，还必须明确它应该随哪一个对象更新。

本轮对上一轮结论的一个收紧

插件目录的 work prompt 确实包含 interactionmode 的条件 include。但 App 的另一个可见 loader 从宿主提供的 runtime 模板目录选取文件，并支持 family fallback。两套材料同时存在，本轮没有证明每个会话最终走哪条模板路径。因此不能将“发现某段模板”直接等同于“当前系统提示词”。S07S08

上下文类型为什么需要它失效或更新边界
System template定义通用工作方式模式、产品版本、模板目录
User context注入身份、口吻、个性化用户/专家身份、首条上下文与恢复
Working history维持当前任务因果关系取消、工具结果补齐、摘要边界
Memory跨轮或跨项目复用信息作用域、写策略、功能开关
Skill + references在命中时补充方法与领域知识触发、版本、资源路径与同名覆盖

04

Skill 如何进入执行上下文

先发现候选，再选择方法，最后绑定资源和工具。

  1. 发现与去重

    lite-wb 的一个目录 provider 按 project → user → connector → session skill dirs → bundled 扫描；先出现的同名条目优先，bundled 补缺，并缓存加载结果与进行中的 Promise。此结论只覆盖该 provider，不能扩展成整个插件系统的统一优先级。S10

  2. 选择与渐进读取

    作者指南规定先用 name/description 描述候选，触发后读取 SKILL.md，再按需读取 references 或使用 scripts/assets。这能减少无关说明进入本轮；模型是否每次正确触发没有运行证据。S09

  3. 绑定领域能力

    SheetAgent plugin.json 同时声明 commands、skills、hooks、MCP server。Skill 提供“何时怎样做”，MCP 提供动作接口，Hook 接到生命周期事件。S11

  4. 按会话过滤工具

    builtin tool policy 区分 eager、deferred 和 explicit-only；ToolSearch 不会自动放行 explicit-only 工具。MCP 层另有 enabled、trusted 与 session 可见性条件。S21S22

“加载 Skill”与“获得权限”不是同一个事件。一个 Skill 能描述某工具，并不意味着当前会话已连接它、已取得凭据，或获准执行其中每个动作。

本轮同时核对了 lite-wb 与 headless 中的部分同类逻辑。启动脚本包含两种 bundle 分支，但未读取当前进程启动参数，所以报告把 CLI 结论限制为“随安装交付的可见实现”。S35

05

从用户意图到执行路径

切换下面的案例，查看交付物、修改边界和执行方式如何改变。

根据旧销售表，另做一份月度汇总 xlsx

识别独立交付物 → 加载 sheet-generation → 提取参考内容 → 按 schema/pattern 建表 → 重算与 JSON 校验 → 交付新工作簿

路由的决定因素是“新路径上的独立工作簿”，不是是否附带 Excel。参考素材交给生成 Skill 处理；生成流程使用规范和场景模式组织工作，再验证公式结果。

边界：源文件是内容来源，不能顺手修改。

在这份工作簿里增加月度汇总 sheet

识别原文件编辑 → 解析文件/实例身份 → 加载 sheetagent Skill → 委派完整任务 → 领域工具修改 → 保存并返回结果

交付物仍是原工作簿，因此不走新建表格路线。需要理解与汇总数据的任务交给 sheet-agent；指定单元格的确定性小修改可走 local-office-edit。

边界：Router、handler 和 Agent 对 file_id 的交接要求存在差异，见下面的静态反例。

从零制作一份较完整的专业 DOCX 报告

DOCX 入口 → Orchestrator 判断 → writer 产出 Markdown → formatter 产出 HTML → converter 输出 DOCX → 保存与预览

常规链按产物类型串接；orchestrator 负责交接字段和状态记录，下层负责领域决策。默认采用角色切换，并非每阶段都启动独立子 Agent。

边界：HTML 检查失败后仅修正一次且不复检；audit trail 不等于事务或恢复引擎。

起草约 600 字的文稿并交付 DOCX

确认无既有文档 → 判断目标短于 1000 字 → brief-compose → 撰稿并生成 HTML → 转换 DOCX → 展示最终文件

这个条件命中后，orchestrator 明确优先转入 brief-compose，无需继续常规多角色编排。它仍要求转换与交付，而不是只在聊天中贴正文。

边界：短路径是一套单独约定，不能从“有三个 Stage”推断所有 DOCX 请求都走三个 Stage。

“做一张海报”还不足以确定执行引擎

读取用户交付意图 → 判断图层还是像素 → Ardot 或 Miora → 加载同族 core → 加载一个 domain → 执行对应领域流程

需要可编辑文字、布局和图层时属于 Ardot；需要完成的生成图片/视频时属于 Miora。两种 core 的操作流程不同，不能交叉拼接。

边界：当意图不足以区分两者时，路由约定要求澄清；名称相同不代表产物类型相同。

这是对包内流程文本的解释器，不会读取文档、调用工具或启动 WorkBuddy。选项仅覆盖报告选取的案例。

发现一处跨文件契约不一致

上层 ROUTER

先解析 live file_id

要求主 Agent 解析 ID 后交给子 Agent，后者不应再打开文件或解析路径。S12

中间 SKILL

交接列表没有 ID

excel-handler 只列路径、原始请求、时间、预期返回四项，且要求不要添加实现细节。S13

下层 AGENT

方法层的分工，不等于运行时层的隔离。

07

工具执行被包装成可观测的事件

动作前后的 Hook 能扩展行为，但不能替代全部运行时约束。

动作提出name + arguments + callId
→
前置策略 / Hook决定、修改输入、提供原因
→
执行与后置 Hookresult / error / additionalContext

CLI 的可见 Hook helper 支持 PreToolUse 的许可决定与输入修改，PostToolUse 的附加上下文和输出修改，并按 callId 报告耗时与成功/错误事件。这里展示的是扩展面，未完整验证 Hook 与所有权限门禁的调用先后。S23

保存被绑定到生命周期

SheetAgent 的 SubagentStop Hook 关联保存脚本。脚本查询编辑器状态，保存脏文件，对占用状态作有限重试。这降低了“模型回复完成，但文件未保存”的风险；真实保存成功率没有测量。S11S27

异常策略决定扩展的强度

同一个 PreToolUse helper 在 Hook 执行异常时记录错误并返回 allowed=true。说明至少这个扩展点偏向不中断工作，不能把它单独当成强制安全门禁；其他权限与 sandbox 层仍需独立判断。S23

08

完成状态必须和交付证据绑定

过程成功、结果正确、用户可用，是三个验收问题。

PROCESS

工具是否执行完

退出码、transport 完成、result/error。这只能说明机制层发生了什么。

RESULT

产物是否满足规则

公式重算状态、结构化检测、引用和事实质量。由领域验证定义。

DELIVERY

用户是否得到可用文件

正确路径、保存成功、格式可打开、预览可见；不能只用模型正文宣称。

确定性检查：把能写成规则的部分落地

HTML review 的实际脚本综合六个维度，安全性与各维度阈值共同决定 passed。Excel 流程要求重算并检查 JSON status、total_errors，避免 exit=0 被误当成公式零错误。S24S25S26

有界修正：控制成本，也留下质量缺口

HTML review 规定失败后只修正一次，之后直接输出而不复检。因此“已修正”和“复检通过”应是不同状态。建议自己的系统用固定修正预算，并在预算耗尽时准确保留未验证状态。S24

研究核查的一个可推演反例

research workflow 对每个 claim 做三次判断，至少两份有效返回才能保留；但未保留条目统一归入 killed，报告再标为 refuted。下方按该分支作纯逻辑演示，没有运行任何模型。S20

“未推翻”并不等于“证实”；多个模型判断也不一定相互独立。此处建议的三态分类是本报告的分析建议，不是 WorkBuddy 已实现的行为。

09

长任务靠历史工程维持连续性

工作历史与长期记忆解决不同问题。

实现

历史先整理，再送给模型

HistoryAgentRunInterceptor 取当前 Agent 的相关历史，处理 session 分隔、已取消输入、压缩边界、任务与错误消息，并补齐工具调用结果关系。压缩后还会处理 user context 的恢复。S28

压缩路径能尝试摘要、采用工程压缩回退；失败或取消时有恢复原 history 的分支。它处理的是“有限上下文怎样延续任务”，不等于长期记忆学习。S29

约定

记忆按作用域和写入责任拆开

模板区分云端画像/历史检索、用户级本地记忆、项目级工作日志与长期笔记。用户级和项目级内容受功能开关控制，写入策略不同。S30

这些规则说明设计意图；本轮未读取用户记忆、验证云端归纳质量或证实具体开关已开启。

摘要是有损信息处理。即便有回退代码，也不能宣称任务意图、证据链和所有未完成动作都被无损保留。可借鉴的工程要求是给摘要保留来源边界、当前目标、未完成动作和可恢复证据。

10

恢复连接，不等于重做业务

这是本轮最值得学习的运行时边界之一。

资源获取

预热只是加速层

池命中先校验环境，再激活会话；未命中或激活失败回退冷启动。环境不一致的候选会淘汰，避免将旧环境直接复用给新会话。S02S03

业务恢复

发送状态未知时避免自动重放

本地 ACP 拒连类错误会重置并重试一次；reset、timeout、stream ended 等错误被标记为 after_send_or_unknown / replay unsafe，重置后留待下一次显式请求。S33S34

具体问题可见机制为什么重要
旧 runtime 的晚到回调runtimeOwnershipEpoch + activeCallbackClients 双重检查重连后旧结果不会直接更新当前会话。S31
取消操作等待期间来了新请求cancel 保存 promptSeq，初始化后再次比较防止一个延迟取消伤及新请求。S32
多个 MCP 同时断线重连并发上限与带抖动指数退避减少同一时刻反复重连的压力。S22
浏览器/native runtime 交接sessionId、pluginRoot、version、leaseId 检查让资源归属成为显式协议字段。S36

重试必须根据业务是否可能已经发生来分类。 ECONNREFUSED 与“发出后断流”在此代码中走不同策略。这个区分有价值，但仅凭静态错误分类不能证明 exactly-once，也未完成重复写入的故障注入验证。
